## 1. createServerAction の実装本体

定義場所: `/Users/haru/ghq/github.com/harusame-dev/formawork.ai/apps/web/libs/create-server-action.ts`

6つのオーバーロード（Public/Private × schema有無 × role有無）と1つの実装を持つ。実装本体（`:168-253`）:

```ts
// 実装
export function createServerAction&lt;
  TSchema extends v.GenericSchema,
  TData,
  TError extends string,
&gt;(
  logicFunction: (input: any, context: any) =&gt; Promise&lt;Result&lt;TData, TError&gt;&gt;,
  options:
    | PublicOptions&lt;TSchema, TData, TError&gt;
    | PrivateOptions&lt;TSchema, TData, TError, UserRole&gt;,
): (input?: v.InferInput&lt;TSchema&gt;) =&gt; Promise&lt;Result&lt;TData, TError | ServerActionErrorMessage&gt;&gt; {
  return async (input?) =&gt; {
    const logger = await getLogger(options.name);
    logger.info(`${options.name} を実行`, { input });

    // (1) バリデーション
    let validatedInput = input;
    if (options.schema) {
      const parseResult = valibot.safeParse(options.schema, input);
      if (!parseResult.success) {
        logger.warn("バリデーション失敗", { event: EventType.InputValidationError, issues: parseResult.issues });
        return fail(VALIDATION_ERROR_MESSAGE);  // "入力内容に誤りがあります"
      }
      validatedInput = parseResult.output;
    }

    // (2) 認証・認可
    let context;
    if (options.isPublic) {
      context = { logger, role: null, userId: null };
    } else {
      const userId = await getUserStaffId();
      if (!userId) {
        logger.warn("認証されていないアクセス", { event: EventType.AuthenticationFailure });
        return fail(UNAUTHORIZED_ERROR_MESSAGE);  // "認証に失敗しました"
      }
      const role = await getUserRole();
      if ("role" in options &amp;&amp; options.role &amp;&amp; options.role.length &gt; 0 &amp;&amp; !options.role.includes(role)) {
        logger.warn("権限がないアクセス", { event: EventType.AuthorizationError });
        return fail(FORBIDDEN_ERROR_MESSAGE);  // "この操作を実行する権限がありません"
      }
      context = { logger, role, userId };
    }

    // (3) ユースケース呼び出し
    try {
      const result = await logicFunction(validatedInput, context);
      if (result.success) {
        logger.info(`${options.name} 成功`);
        await options.onSuccess?.({ input: validatedInput, result: result.data });
      } else {
        logger.warn(`${options.name} 失敗`, { error: result.error });
        await options.onFailure?.({ error: result.error, input: validatedInput });
      }
      return result;
    } catch (error) {
      unstable_rethrow(error);  // redirect() 等の Next.js 制御例外を再スロー
      logger.error(`${options.name} で予期しないエラーが発生`, { err: error });
      return fail(INTERNAL_SERVER_ERROR_MESSAGE);
    }
  };
}
```

### 引数の型と意味

第1引数 `logicFunction`: 実ユースケース。`(input, context) =&gt; Promise&lt;Result&lt;TData, TError&gt;&gt;`。`input` は valibot 検証済みの値、`context` は下記。

第2引数 `options`（`BaseOptions` + Public/Private 派生、`:30-63`）:
- `name: string` — ロガー名・ログメッセージに使用（必須）
- `schema?: TSchema` — valibot スキーマ。あれば `safeParse` で検証
- `onSuccess?: ({ input, result }) =&gt; void | Promise&lt;void&gt;` — 成功時フック（例: `updateTag` / `redirect`）
- `onFailure?: ({ error, input }) =&gt; void | Promise&lt;void&gt;` — 失敗時フック
- `isPublic?: false` / `isPublic: true` — `true` で認証スキップ（Public）
- `role?: TRole[]` — 許可ロールの配列（Private のみ）

`context` の型（`:18-28`）:
```ts
interface PublicServerActionContext { logger: Logger; role: null; userId: null; }
interface PrivateServerActionContext&lt;TRole extends UserRole = UserRole&gt; { logger: Logger; role: TRole; userId: string; }
```

### role による認可

`:214-225`。`getUserRole()` で現在ユーザーのロールを取得し、`options.role` 配列に含まれなければ `FORBIDDEN_ERROR_MESSAGE` を `fail` で返す。`role` 未指定なら認証のみ（ログインしていれば誰でも可）。`role: [UserRole.Admin]` のように指定する（例: `register-staff.action.ts:18`）。

## 3. 認可ヘルパー

専用の「リソースアクセス可否判定ヘルパー（例: canAccessProject）」は**存在しない**。認可は2層:

1. **ルートレベル**: `apps/web/proxy.ts:70-76` — 未ログインかつ非Publicページは `/login` へリダイレクト（Public は `/login` と `/lp` のみ、`:67-68`）。
2. **アクションレベル**: createServerAction の `role` オプションによるロール認可（セクション1参照）。`role: [UserRole.Admin]` の唯一の使用箇所は staff 系アクション。

**リソース所有権チェックは各 logicFunction 内で個別に DB 照会して実装している**。例 `customer-memory/edit/edit-customer-memory.ts`:
```ts
const memories = await db.select({ id: customerMemoriesTable.id })
  .from(customerMemoriesTable).where(eq(customerMemoriesTable.id, input.memoryId)).limit(1);
if (!memories[0]) return fail("メモリが存在しません");
```
存在確認止まりで「ユーザー × リソース」の細粒度認可ヘルパーはまだ無い。プロジェクト可視性（Public/Private、招待者のみ）に基づくアクセス制御を新規実装する場合、**logicFunction 内で `context.userId` を使って DB 照会して判定する**のが既存パターンに沿う（CLAUDE.md の「認可は RLS ではなくアプリ層 createServerAction で実施」とも整合）。

## 5. 外部API/ライブラリ呼び出しの規約

`agent-docs/外部ライブラリの使用.md` の要点:
- 外部ライブラリは API 変更・乗り換えに備え、**原則アプリに必要なユースケースに絞った薄いラッパーを作成し直接呼び出さない**
- ただし**過度に複雑になる場合は直接呼び出しも許容**
- ラッパーにテストを書くことで依存自動更新時の破壊的変更を検知できる
- 例として `date.ts` に `formatDate()` を切り出し、利用側はラッパー経由で呼ぶ形を提示

ただし CLAUDE.md（プロジェクト指示）には **「AI 英訳：Claude API（公式 SDK を直接利用。抽象化層は設けない）」** と明記されており、Claude/OpenAI SDK についてはラッパー方針の**例外**として直接利用が指定されている点に注意。

### 既存の薄いラッパー実例

外部 SDK ラッパーの代表例は **auth ドメインの Supabase ラッパー**:
- `Auth` / `AuthAdmin` インターフェース（`auth.ts` / `auth-admin.ts`）で必要ユースケースのみ定義
- `SupabaseAuth` / `SupabaseAuthAdmin` クラスが `@supabase/supabase-js` を内部実装に閉じ込め、戻り値を全て `Result&lt;…, AuthError&gt;` に正規化（`supabase-auth.ts` 全体）
- ファクトリ `getAuth()` / `getAuthAdmin()` で生成

`packages/supabase/src/admin.ts` も `createClient` を `createAdminClient()` でラップしつつ config 関数経由でキー注入する型。Anthropic/OpenAI SDK ラッパーを作る場合、この `interface + Supabase実装クラス + ファクトリ関数 + Result 戻り値` の型が既存最寄りパターン（ただし CLAUDE.md 指示により Claude SDK は直接利用も可）。

現状リポジトリに **anthropic / openai / embedding / pgvector のコード実装はまだ存在しない**（grep ヒット0）。これから新規追加するフェーズ。

## 6. Result 型

パッケージ: `@harusame0616/result`（v0.1.3）。定義 `node_modules/.pnpm/@harusame0616+result@0.1.3/.../dist/result.d.ts`。

```ts
export type Success&lt;T&gt; = { success: true; data: T };
export type Failure&lt;E&gt; = { success: false; error: E };
export type Result&lt;T, E&gt; = Success&lt;T&gt; | Failure&lt;E&gt;;

export declare function succeed(): Success&lt;undefined&gt;;
export declare function succeed&lt;T&gt;(data: T): Success&lt;T&gt;;
export declare function fail&lt;E&gt;(error: E): Failure&lt;E&gt;;

// 例外を Result に変換するヘルパー
export declare function tryCatch&lt;T, E = Error&gt;(fn, onError?): Result&lt;…&gt;;
export declare function tryCatchAsync&lt;T, E = Error&gt;(fn, onError?): Promise&lt;Result&lt;…&gt;&gt;;

// 型ヘルパー
export type ExcludeFailure&lt;T&gt;, ExtractSuccessType&lt;T&gt;, ExtractFailure&lt;T&gt;;
```

### 使い方（実コード）

判定は `result.success` で分岐。成功は `result.data`、失敗は `result.error`。エラーは多くの場合 string リテラルのユニオン型で表現。

`edit-customer-memory.ts`:
```ts
import { fail, type Result, succeed } from "@harusame0616/result";
type ErrorMessage = "メモリが存在しません" | "メモリの更新に失敗しました";

export async function editCustomerMemory(input): Promise&lt;Result&lt;void, ErrorMessage&gt;&gt; {
  if (!memories[0]) return fail("メモリが存在しません");
  await db.update(...)...;
  return succeed();  // 引数なし succeed は Success&lt;undefined&gt;
}
```

`register-staff.ts`（`tryCatchAsync` + throw でトランザクションエラーを Result 化する応用例）:
```ts
import { type Result, succeed, tryCatchAsync } from "@harusame0616/result";

return tryCatchAsync(() =&gt;
  db.transaction(async (tx) =&gt; {
    ...
    if (!result.success) {
      if (result.error === AuthError.EmailExists) throw EMAIL_EXISTS_ERROR;
      throw CREATE_AUTH_ERROR;
    }
    return succeed({ staffId });
  }),
);
```

createServerAction はこの `Result` を返り値契約として要求し、`result.success` に応じて onSuccess/onFailure を呼ぶ（セクション1）。`AuthError` も列挙型として `auth-error.ts` にあり、エラー値に使われる。

## 2. Server Action の書き方

`createServerAction(ユースケース, options)` を呼ぶだけ。`options` は `name`（ロガー名）、`schema`（valibot）、`role`（認可）、`onSuccess`（`updateTag` + `redirect`）。

`register-customer.action.ts:1-20`（最も標準的な例、完全引用）:

```ts
"use server";

import { updateTag } from "next/cache";
import { redirect } from "next/navigation";
import { UserRole } from "@/features/auth/get-user-role";
import { createServerAction } from "@/libs/create-server-action";
import { CustomerTag } from "@/features/customer/tag";
import { registerCustomer } from "./register-customer";
import { registerCustomerSchema } from "./schema";

export const registerCustomerAction = createServerAction(registerCustomer, {
  name: "registerCustomerAction",
  onSuccess: ({ result: { customerId } }) =&gt; {
    updateTag(CustomerTag.List);

    redirect(`/customers/${customerId}`);
  },
  role: [UserRole.Admin],
  schema: registerCustomerSchema,
});
```

ポイント:
- `onSuccess` のコールバック引数は `{ input, result }`。register は `result.customerId`（ユースケースが succeed で返した値）を使い、edit/delete は `input.customerId`（バリデーション済み入力）を使う。
- 編集時は関連タグも複数更新 — `edit-customer.action.ts:13-17`:
```ts
  onSuccess: ({ input: { customerId } }) =&gt; {
    updateTag(CustomerTag.List);
    updateTag(CustomerTag.Detail(customerId));

    redirect(`/customers/${customerId}`);
  },
```
- 削除は `RedirectType.replace` で一覧へ。関連タグを全て無効化 — `delete-customer.action.ts:11-26`:
```ts
const deleteCustomerSchema = v.object({
  customerId: v.pipe(v.string(), v.uuid()),
});

export const deleteCustomerAction = createServerAction(deleteCustomer, {
  name: "deleteCustomerAction",
  onSuccess: ({ input: { customerId } }) =&gt; {
    updateTag(CustomerTag.List);
    updateTag(CustomerTag.Detail(customerId));
    updateTag(CustomerTag.NotesByCustomerId(customerId));
    updateTag(CustomerTag.MemoriesByCustomerId(customerId));

    redirect("/customers", RedirectType.replace);
  },
  role: [UserRole.Admin],
  schema: deleteCustomerSchema,
});
```
  （delete のように小さい1フィールドスキーマは action.ts 内にインライン定義してよい。）

- インラインでユースケースをラップして `context.userId` を使い、`after()` で副作用をトリガーする変種 — `register-customer-note.action.ts:31-57`:
```ts
export const registerCustomerNoteAction = createServerAction(
  async (input, { userId }) =&gt; {
    const result = await registerCustomerNote({
      ...input,
      staffId: userId,
    });

    if (!result.success) {
      return result;
    }

    after(async () =&gt; {
      await Promise.allSettled([processAdviceQueue(), processMemoryQueue()]);
    });

    return result;
  },
  {
    name: "registerCustomerNoteAction",
    onSuccess: ({ input: { customerId } }) =&gt; {
      updateTag(CustomerTag.NotesByCustomerId(customerId));
    },
    schema: registerCustomerNoteSchema,
  },
);
```
  （`role` を省略すると認証のみ・認可なし。`isPublic: true` で未認証許可。）

### createServerAction の挙動（`apps/web/libs/create-server-action.ts`）

ジェネレートされる Action の処理順（実装 `:182-252`）:
1. ロガー生成・input ログ（`:185-186`）
2. `options.schema` があれば `valibot.safeParse` → 失敗で `fail("入力内容に誤りがあります")`（`:190-200`）
3. `isPublic` でなければ `getUserStaffId()` で認証（無ければ `fail("認証に失敗しました")`）→ `getUserRole()` で `options.role` 照合（不一致は `fail("この操作を実行する権限がありません")`）（`:202-227`）
4. `logicFunction(validatedInput, context)` 実行。`context` は `{ logger, role, userId }`（`:230`）
5. `result.success` で `onSuccess`、失敗で `onFailure` を呼ぶ（`:232-245`）
6. 例外は `unstable_rethrow(error)`（redirect 等を素通し）後 `fail("サーバーエラー...")`（`:247-251`）

戻り値型は `Promise&lt;Result&lt;TData, TError | ServerActionErrorMessage&gt;&gt;`。6 つのオーバーロード（Public/Private × schema有無 × role有無）で型付け（`:71-165`）。

## 3. ユースケース層（サフィックスなし `.ts`）

`@harusame0616/result` の `Result&lt;T, E&gt;` / `succeed()` / `fail()` を返す。DB は `@workspace/db/client` の `db`。

成功のみの登録 — `register-customer.ts:1-36`（完全引用）:

```ts
import { type Success, succeed } from "@harusame0616/result";
import { db } from "@workspace/db/client";
import { customersTable } from "@workspace/db/schema/customer";
import { generateUniqueId } from "@/libs/generate-unique-id";
import type { RegisterCustomerParams as RegisterCustomerParameters } from "./schema";

export async function registerCustomer({
  address, birthDate, email, firstName, firstNameKana, gender,
  lastName, lastNameKana, phone, remarks,
}: RegisterCustomerParameters): Promise&lt;Success&lt;{ customerId: string }&gt;&gt; {
  const customerId = generateUniqueId();

  await db.insert(customersTable).values({
    address,
    birthDate: birthDate || null,
    customerId,
    email, firstName, firstNameKana, gender,
    lastName, lastNameKana, phone, remarks,
  });

  return succeed({ customerId });
}
```

エラーハンドリングあり（存在チェック → `fail`）— `edit-customer.ts:11-61`:

```ts
const CUSTOMER_NOT_FOUND_ERROR_MESSAGE = "指定された顧客が見つかりません" as const;

export async function editCustomer({
  address, birthDate, customerId, email, /* ... */ remarks,
}: EditCustomerParameters): Promise&lt;
  Result&lt;undefined, typeof CUSTOMER_NOT_FOUND_ERROR_MESSAGE&gt;
&gt; {
  const logger = await getLogger("editCustomer");

  const customer = await db.query.customersTable.findFirst({
    where: eq(customersTable.customerId, customerId),
  });

  if (!customer) {
    logger.warn("顧客が見つかりません", { customerId });
    return fail(CUSTOMER_NOT_FOUND_ERROR_MESSAGE);
  }

  await db
    .update(customersTable)
    .set({ address, birthDate: birthDate || null, email, /* ... */ remarks })
    .where(eq(customersTable.customerId, customerId));

  logger.info("顧客情報の更新に成功", { action: "edit-customer", customerId });

  return succeed();
}
```

ポイント / 規約:
- エラーメッセージは `const ... = "..." as const` で定義し、Result のエラー型に `typeof X` で渡す（型安全なエラー）。
- ロガーは `getLogger("関数名")`（`@repo/logger/nextjs/server`）。`logger.warn/info/error` に第2引数で構造化メタ。
- Drizzle は2スタイル混在: クエリビルダ `db.select().from().where(eq(...)).limit(1)`（`delete-customer.ts:30-34`）と リレーショナル `db.query.table.findFirst({ where })`（`edit-customer.ts:28-30`）。
- トランザクション・Storage・キューを束ねる例 — `register-customer-note.ts:48-103`: `db.transaction(async (tx) =&gt; { ... })` 内で insert → `supabase.storage.from(BUCKET).move()` → `new PgmqQueue(..., tx).sendMessage()`。Storage 管理クライアントは `createAdminClient()`（`@repo/supabase/admin`）。
- 削除時の関連 Storage クリーンアップは `Promise.allSettled` で並列・失敗を握り潰しログ（`delete-customer.ts:74-88`）。
