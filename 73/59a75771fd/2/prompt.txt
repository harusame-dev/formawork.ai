## 1. nextjs-アーキテクチャガイドライン.md
パス: `/Users/haru/ghq/github.com/harusame-dev/formawork.ai/agent-docs/nextjs-アーキテクチャガイドライン.md`

- **Server Component First**: Server Component 実装を最優先。ユーザーインタラクションが必要なときだけ Client Component を採用する。
- **データ取得は末端で**: 上位でまとめて取得して下位へバケツリレーするのを避け、必要とする末端で取得する。
- **層の使い分け（mutation/fetch の振り分け）**:
  - ミューテーション → **Server Action**
  - Server Component 用のデータ取得には Server Action を使わない
  - Server Action でカバーできないもの・クライアントからのデータフェッチ API → **Route Handler**
  - cron 用など外部利用想定 API・ミューテーションを伴わないサーバー操作 → **Route Handler**
- **Server Action は実質 API**: 自由なパラメータで呼べるため、引数があるものは必ずバリデーション・認証・認可を実施する。
- 注記: このドキュメント自体は action/usecase/query の細分化には触れていない。usecase 切り出しは CLAUDE.md の `.claude/rules/nextjs-server-action.md`（認証・認可・バリデーション・パラメータ変換・ユースケース呼び出しのみが Server Action の責務）が規定。

## 2. Nextjs-キャッシュ戦略ガイドライン.md
パス: `/Users/haru/ghq/github.com/harusame-dev/formawork.ai/agent-docs/Nextjs-キャッシュ戦略ガイドライン.md`

- **3 つの cache ディレクティブを使い分ける**:
  - `use cache`: 静的・全ユーザー共有・リクエスト非依存のコンテンツ（ビルド時事前レンダリング）。cookies/headers にアクセス不可。
  - `use cache: remote`: 動的コンテキストで共有されるが毎リクエストレンダリングが必要なコンテンツ、高価な処理のサーバー側キャッシュ（`await connection()` 後など）。
  - `use cache: private`: Cookie/ヘッダーで変わるユーザー個別コンテンツ。クライアント側のみ保存・ユーザーごとに分離。
- **cacheLife（revalidate / タグ運用）**:
  - **アプリで更新を制御できるデータ**（DB・webhook 検知可能）: カスタムプロファイル **`permanent`** を使い、更新タイミングで **`revalidateTag()`** を実行する。
  - **`cacheTag()`** で更新タイミングに応じたタグを設定する（例: `cacheTag("parent-delete", "foo-update")`）。
  - **更新タイミングを制御できないデータ**（外部 API 等、一定間隔更新で十分）: `"hours"`・`"days"`・カスタム時間など要件に応じた時間指定にする。

## 1. Drizzle スキーマの定義場所・分割方法

**場所**: `packages/db/src/schema/` 配下。**1ファイル = 1ドメイン**（厳密に1テーブルではなく、関連する複数テーブルを同居）。例: `customer-note.ts` には `customerNotesTable` と `customerNoteImagesTable` の2テーブルが入っている。

**まとめ方**: `packages/db/src/schema/index.ts:1-5` で全ファイルを re-export。

```ts

export * from "./customer-memory";
export * from "./customer-note";
export * from "./customer-note-advice";
```

さらに `packages/db/package.json:6-16` の `exports` でファイル単位の subpath export も定義（`./schema/customer` 等）。**新テーブル追加時は index.ts と package.json の両方に追記が必要**。

### 命名規則（重要）
- **スキーマ定義キー = camelCase / DBカラム名 = snake_case**。`text("content")` のように第1引数に snake_case 名を明示。
- **テーブル変数名は `xxxTable` サフィックス**（`customersTable`, `customerNotesTable`）。
- **テーブル物理名は複数形 snake_case**（`"customers"`, `"customer_notes"`, `"customer_note_advice"`）。
- **id 型は `uuid`**。`serial`/`integer` の自動採番 PK は不使用。PK 名はテーブルごとに `customerId`/`customerNoteId`/`staffId`/`id` と揺れあり（CATツールでは `id` 統一が無難）。
- **`created_at`/`updated_at` の付け方が定型**（後述）。

### 代表的なテーブル定義の丸ごと引用

`packages/db/src/schema/customer-note.ts:19-45`:

```ts
export const customerNotesTable = pgSchema(schemaName)
  .table(
    "customer_notes",
    {
      content: text("content").notNull(),
      createdAt: timestamp("created_at").defaultNow().notNull(),
      customerId: uuid("customer_id")
        .notNull()
        .references(() =&gt; customersTable.customerId, { onDelete: "cascade" }),
      customerNoteId: uuid("customer_note_id").primaryKey().defaultRandom(),
      serviceDate: date("service_date").notNull(),
      staffId: uuid("staff_id")
        .notNull()
        .references(() =&gt; staffsTable.staffId, { onDelete: "cascade" }),
      updatedAt: timestamp("updated_at")
        .defaultNow()
        .notNull()
        .$onUpdate(() =&gt; new Date()),
    },
    (table) =&gt; [
      index("idx_customer_notes_customer_service_date").on(
        table.customerId,
        table.serviceDate.desc(),
      ),
    ],
  )
  .enableRLS();

export type SelectCustomerNote = typeof customerNotesTable.$inferSelect;
export type InsertCustomerNote = typeof customerNotesTable.$inferInsert;
```

**定型パターン（CATツール各テーブルでもこれを踏襲すべき）**:
- `pgSchema(schemaName).table("物理名", {...columns}, (table) =&gt; [...indexes]).enableRLS()`
- `schemaName` は `packages/db/src/pgschema.ts` の `import { schemaName } from "../pgschema"`（`.claude/rules/db-schema.md` で必須化）。
- **必ず `.enableRLS()` を付ける**（`.claude/rules/db-schema.md`: 新テーブルは RLS 有効化。ただしポリシーは作らず認可はアプリ層で実施）。
- **`created_at`**: `timestamp("created_at").defaultNow().notNull()`
- **`updated_at`**: `timestamp("updated_at").defaultNow().notNull().$onUpdate(() =&gt; new Date())`
- **PK uuid**: `uuid("id").primaryKey().defaultRandom()`（`customers` だけはアプリ側採番で `.defaultRandom()` 無し: `customer.ts:21`）
- ファイル末尾で `Select{Name}` / `Insert{Name}` 型を `$inferSelect`/`$inferInsert` で export。

インデックスのコールバックは配列形式（`customer-note.ts:38`）と旧来のオブジェクト形式（`customer-memory.ts:56` の `{ customerCategoryIdx: index(...) }`）が混在。**新規は配列形式が推奨**。

```sql
  PERFORM set_config('search_path', current_setting('app.saved_search_path'), false);
END $$;
```
ポイント: `CREATE EXTENSION ... WITH SCHEMA extensions`（Supabase 慣例）＋ search_path 退避・復元で囲む。手書き SQL 追加後は `drizzle/meta/_journal.json` への手動エントリ追記も必要（既存の 0001/0002 が手動追加されている）。

**vector カラムの表現**: Drizzle 標準型に `vector` は無いため、`drizzle-orm/pg-core` の `customType`（現状未使用）で `vector(N)` を自前定義するか、SQL マイグレーションで `ADD COLUMN embedding vector(N)` + HNSW/IVFFlat インデックスを手書きする方針になる。`customers.ts:26-29` で `generatedAlwaysAs` + `sql\`\`` を使った前例があり、`sql` テンプレートでの拡張的カラム表現には慣れている。

## 5. enum / リレーション（外部キー）の定義パターン

### enum: `pgEnum` は不使用。smallint + const オブジェクトで表現
`grep` で `pgEnum` ヒットなし。代わりに **`smallint` カラム + TypeScript の `as const` オブジェクト + ラベル Record** で擬似 enum を構成。

`packages/db/src/schema/customer-memory.ts:16-49`:
```ts
export const MemoryCategory = {
  Communication: 4, Conversion: 3, Event: 5,
  Health: 6, Personal: 1, Preference: 2,
} as const;
export type MemoryCategory = (typeof MemoryCategory)[keyof typeof MemoryCategory];
export const MEMORY_CATEGORY_LABEL: Record&lt;MemoryCategory, string&gt; = {
  [MemoryCategory.Personal]: "パーソナル情報", /* ... */
};
// テーブル側:
category: smallint("category").notNull(),
```
`gender` も同様に `smallint("gender").notNull().default(1)`（`customer.ts:34`）。**CATツールの status 等も pgEnum でなく smallint + const が既存規約に沿う**。

jsonb の型付けは `.$type&lt;T&gt;()` を使用（`customer-note-advice.ts:66`: `jsonb("advice").$type&lt;AdviceContent&gt;().notNull()`）。

### リレーション（外部キー）: カラム定義に `.references()` をインライン
Drizzle の `relations()` ヘルパーは未使用。**FK はカラムに直接 `.references(() =&gt; 親Table.親カラム, { onDelete: "cascade" })`**。

`customer-note.ts:25-27` / `52-56`:
```ts
customerId: uuid("customer_id")
  .notNull()
  .references(() =&gt; customersTable.customerId, { onDelete: "cascade" }),
// ...
customerNoteId: uuid("customer_note_id")
  .notNull()
  .references(() =&gt; customerNotesTable.customerNoteId, { onDelete: "cascade" }),
```
- 親テーブルは `import { customersTable } from "./customer"` で取り込む。
- `onDelete: "cascade"` が基本。
- 複合 PK は `primaryKey({ columns: [table.a, table.b] })`（`customer-note.ts:61`）。
- 例外的に FK を張らないケースあり（`staff.ts:9-11` の `authUserId` は auth.users へ FK 張らず `.unique()` のみ、理由コメントあり）。
